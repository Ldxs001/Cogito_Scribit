约束解码（给模型一个固定 schema，让它只填空不自由发挥）保证的是「输出长什么样」，不保证每个消费环节都按那个长相去读。v0.41.1 的事故是：出口归一化层按quote/problem两种键判问题是否存活，而承诺项的输出契约是五键（line/promise/how/speaker/close_after），于是模型报的每一条承诺问题在归一化里被continue丢掉，承诺链永远指不出落点、永远红。本文只讲这一个盲区：schema 是统一推动点，但只有定义处和每一处消费都尊重它，契约才不是摆设。

01引子：真实起点

写稿门禁里有一条承诺链检：模型报出「这句承诺了某件事却没做到」，程序应据此定点修补。某次跑批，报告上承诺链整条红着——可点开详情，却写着「通过」[1]。

结论、详情、清单三项自相矛盾：判不通过，却一个具体句子都指不出来。那种红是没道理的红——它红的不是「有问题」，而是「有问题但说不清问题在哪」。

没道理的红还有一个副作用，比错杀更耗人：它让「红」这个信号贬值。语义项的红是真红（有清单、有落点、修得动），承诺项的红是空红（无清单、无落点、无从下手）——两种红混在同一个报告里，读到它的人只能每次都人工分辨「这个红要不要管」，信号系统等于失效了一半。修复后红与红同构：每条红都带得动一次定点修，信号重新值得信任。

02现象：它到底长什么样

承诺链检的清单永远为空。实测记录（projects/20260917-015336/过程/2a|2c）：check_promise两次ok=false且issues=0，detail还写着「通过」[1]。

patch_targets等的是「带句号（落点）的问题」——能不能定点修，看问题有没有锚到具体一句。它收到的却是空清单，当场break，报告上的承诺链于是永远红着。链路从「检报」到「定点修」这一段，整段断了。

约束解码：给模型一个固定 schema（字段与枚举），让它只填空、不自由发挥。它约束的是「输出长什么样」。 归一化：把模型在各轮、各检查段的输出，统一成一条「问题清单」的中间步骤——下游定点修与门禁都从这条清单取数。 落点：被点名的问题具体落在哪一句、用什么锚点去修；没有落点，定点修无从下手。

03错误尝试：我们怎么绕弯的

一开始以为是承诺链检本身没跑对，或者模型没报。但语义检照常工作——它的键本就是quote/problem，与归一化口径一致；副本2a（4 条）→ 2b（8 条）→ 2c（通过）的收敛轨迹清清楚[1]。

焦点于是从「上游没报」转向「下游丢东西」。丢东西的那段，是出口归一化。这条路绕了弯才走到正解：先排除了「模型没报」，才定位到「归一化按另一套契约读」——漏的不是一个字段，是一整类问题的字段契约。

04根因：为什么

根因一句话：script_engine._norm_issues按「两项各自的契约取字段」，却只拿「有没有quote / problem」去判一条问题是否存活；而承诺项的输出契约是line / promise / how / speaker / close_after 五键——天生没有quote和problem，于是模型报的每一条承诺问题都在那一行continue被丢掉（旁边「承诺项多出来的键原样带下去」的代码等于没写）[1]。

一句话：约束解码把字段契约钉死了，下游归一化却按另一套契约去读，契约在消费点断了。 这恰是本书反复讲的那条纪律——统一推动点只定义一次，但每一处消费都必须尊重它；漏掉一个消费点的字段契约，整条链就红得没道理。

契约在消费点断掉，不止这一种断法。同一族病灶在本工具里出现过至少三面：本篇是「schema 漏字段」——输出契约五键，消费点按二键读；#7《定点修补漏接词表》是「枚举嵌套绕过」——schema 的枚举值藏在嵌套数组里，修补层按顶层读；#2 事件（音色默认值两处不一致）是「默认值双份」——定义处一份、工具一份，两份迟早漂。三面共用一个判别式：凡是消费方自己再写一份「字段应该长什么样」，那份私有认知迟早和 schema 分家。所以修法从来不是「把消费点写得聪明些」，而是让消费点除了 schema 之外没有别的字段来源——本篇的修复分支逐字对着五键契约取字段，一个私有拼写都没有。

05正确修法：怎么做对的

修复口径收得很窄：不新增任何分支，只让归一化按两种契约各自取齐说明性字段。收窄的理由值得说透：归一化是出口——所有检查项的问题报告都要从这里过一遍才进清单。出口上的改动，牵一发是全链的：出口多吞一条，全链少一个问题；出口多放一条，下游定点修就多修一处。所以修出口的第一原则是把改动面压到最小——不动语义项的既有路径（它没病），只为承诺项补一个按五键契约取字段的分支，语义检、门禁、定点修三处下游的输入格式一个字节不变。宽改出口看似顺手，实际是把「一处修复」摊成「全链回归」。

5.2 修法本身：两处改动

归一化改为按两种契约取齐说明性字段——quote从quote|promise取，problem从problem|how|promise|text取，五键原样带下[1]。这一步让承诺问题第一次真正进清单。

同时_issues_detail让详情与结论同源：判不通过而一条也报不出来时，详情不再印「通过」，改印「未通过（模型未指出具体句子）」；判通过时空清单照旧念「通过」——三类自相矛盾的源头一并堵[1]。

修好落点之后，承诺链经patch_targets → 定点修 → check_rounds封顶 → 超了直接落盘，与形式门禁同一条路。该分支代码里本就写好，只是从来没被喂进过一条带落点的承诺项，本轮没为它新增任何分支（不降级、不交人工、不早退）[1]。

改前：模型报承诺项(五键) → 归一化按 quote/problem 判存活 → continue 丢光 → 清单空 → 承诺链永远红
    ↓（修复：按两种契约取齐字段，五键带下）
改后：模型报承诺项(五键) → 归一化取齐 quote|promise、problem|how|promise|text → 落点生成 → patch_targets 定点修闭环

图 1：归一化丢落点前后对照（修复前清单恒空，修复后承诺问题首次进清单）[1]。

5.3 归一化修复的骨架

def _norm_issues(raw):                    # raw：模型本轮报出的问题项
    for item in raw:
        if item.get("quote") or item.get("problem"):
            yield normalize_semantic(item)          # 语义项：二键契约，口径本就一致
        elif "line" in item and "promise" in item:
            # 承诺项：五键契约——修复前没有这个分支，全部 continue 丢光
            yield dict(quote=item.get("promise"),
                       problem=item.get("how") or item.get("promise"),
                       **item)                       # 五键原样带下去
        else:
            continue

真实实现见podcast_maker/script_engine.py:_norm_issues（:1696）。修复前只有第一个分支认二键、其余一律continue；修复新增的是中间那个分支——不新增出口、不改语义项路径，五键信息一分不丢地进清单。_issues_detail（:1737）同批收口：判不通过而报不出任何一条时，详情印「未通过（模型未指出具体句子）」，三类自相矛盾在结构上没有并存的余地。

06验证：数据说话

四组证据，测量条件一并给出。

先交代测量位置：本篇所有「清单」「详情」「落点」的观测点都在出口归一化及其下游第一站——清单是patch_targets的直接输入，落点是修补层的直接输入。观测这两站，就等价于观测「承诺链红不红」的全部因果链，中间不存在第三段黑箱。

全量单测 1110 项通过（比上版 +4）[1]：修复的代价只是 4 条新钉，没有引入回归。+4的构成也值得看：不是给_norm_issues补四个 if，是给承诺项补「不被丢」「有落点」「详情同源」「键必留」四个性质断言——性质钉守的是行为不变式，不是实现细节。

新增TestPromiseIssuesSurviveNormalization一组钉子 [1]：① 承诺项缺quote/problem也不被丢（五键齐、落点对）② 能生成patch_targets落点（承诺句 + close_after锚点）——证明走的就是那条老路 ③ 判 fail 且无落点时详情不印「通过」④ 通用钉子：check6_schema要求哪些键，归一化后就得留下哪些键——将来任何一项改了输出契约都能被它当场钉住（script_engine.py:1600即check6_schema，通用钉子守在:1696的_norm_issues）。

副本收敛轨迹（实测）[1]：2a（4 条）→ 2b（8 条）→ 2c（通过）。判得出、定得点、修得动、复判能过——这条轨迹本身就是修复有效的证据。轨迹逐段拆开：

副本问题数状态这一步发生了什么
2a4FAIL修复后首次跑：承诺项进清单、落点可生成，修补层照单定点修
2b8FAIL修完2a的 4 条后复检：暴露更深一层问题（含此前被空清单掩盖的项）
2c0通过收敛：判得出、定得点、修得动、复判能过

值得注意2a→2b是问题数变多：清单从「恒空」变「敢报」，深层问题才有机会浮出来——修复前那条永远红的链，红得连一次定点修都没启动过。

为什么通用钉子比专用钉子值钱 [1]：TestPromiseIssuesSurviveNormalization的前两条是专用钉（承诺项五键、落点生成），第四条是通用钉——check6_schema（script_engine.py:1600）要求哪些键，归一化后（:1696）就得留下哪些键。专用钉守的是这一次的契约；通用钉守的是「任何消费点不得私有缩减字段集」这条元规则——将来语义项或任何新检查项改了输出契约，不用等它红在生产里，提交时就红。

未受影响项 [1]：合成端write_gate_report一字未动（它是记录不是闸门）；语义检未受影响（键本就quote/problem，与归一化口径一致）。修复是收窄，不是牵连。

契约突变实验设计（复跑条件：tests/test_gates.py::TestPromiseIssuesSurviveNormalization，数据[1]）：构造一条五键承诺项{"line": "…", "promise": "…", "how": "…", "speaker": "…", "close_after": …}（天生没有quote/problem），直接喂_norm_issues。旧逻辑下输出清单为空——问题项被continue丢光，精确复现「承诺链永远红」；修复后下清单收下该条：quote/problem取齐、五键原样保留、能生成patch_targets落点。判定标准即该钉子组的四条断言——缺二键不被丢、落点可生成、fail 且无落点时详情不印「通过」、check6_schema要求哪些键归一化后就留哪些键。这组钉子把本实验常态化进 CI：模型端任何一次改输出契约，都会在提交时被当场钉住，而不是等到承诺链红得没道理。

07结语：一句话可复用结论

约束解码不是万能的——它只保证输出长什么样，不保证每个消费点都按那个长相去读。schema 是统一推动点，但只有「定义处 + 每一处消费」都尊重它，契约才不是摆设；漏掉一个消费点的字段契约，整条链就红得没道理。
