# 第 II 部 协作：多个智能体怎么配合

> **读者问题**：单个 LLM 可靠了，多个智能体怎么协作？

第 I 部解决了一个 LLM 的可靠性。但真实世界不是单线程的——你需要检索的智能体、写作的智能体、审计的智能体同时工作，互相传递结果。于是问题变成：**多个 LLM 协作时，谁做决策？**

第 II 部的答案是 08 篇的核心命题：**LLM 只填空，不决策。**

- 决策（选哪条路径、定什么目标、判断什么对）——由链、由架构、由人来做
- LLM 只做一件事：在给定的空位里，填上内容

这就是"有限决策范式"。它来自三个独立构建的智能体（Orchestrator、RAG Assistant、Structured Writer）的共同架构选择——三个系统没有商量，却做出了相同的取舍，这就是"三体印证"：**不是某一个人的偏好，是工程实践逼出来的共同答案。**

08a 篇进一步回答"填空之后怎么保证第一次就做对"：前置规范大于后置验证——把错误空间封堵在生成时刻，而不是生成之后靠检测补救。

08b 篇把问题再推进一步："填空能填多小？"——空是外部考试（LLM/BERT 都是预测模型），空越小容错带越窄、重试概率越大；空的内容不可收束到点（不可穷举性）；U 型注意力（Lost in the Middle）决定空越长中间盲区越大，多阶段分段填空才是正道。验证的分工随之清晰：前置规范只能防自觉（靠模型自身能力）、后置验证防幻觉不可替代（靠审查能力）——多阶段前置 + 非全量验证才是有效过程管控。

08c 篇把问题推到槽位本身："槽位会不会逼 LLM 编造？"——四个论断（槽位比总结靠谱 / 纯子集难适应所有场景 / 槽位太强硬造 / 槽位是减法）+ 三条幻觉治理路径（semantic-split 提示词槽位限定 / RAG Assistant 子集+凝练+代码拼接 / novel-weaver 发散+纠偏）。核心实测：生成式小模型 + 规范 JSON 几乎不幻觉，大模型同样操作幻觉更大。

| 篇 | 解决的问题 |
|----|-----------|
| 08 有限决策范式 | 协作中谁做决策——LLM 只填空，不决策（三体印证） |
| 08a 操作层 | 填空后怎么一次做对——前置规范 > 后置验证 |
| 08b 填空的边界 | 空能填多小——容错宽度 × 注意力窗口双判据，验证按错误类型分工 |
| 08c 槽位的减法 | 槽位会不会逼 LLM 编造——三种场景的幻觉治理路径与四个论断 |

**为什么放在这里**：第 I 部是"单个技能的可靠性"，第 II 部是"多个智能体的协作"，第 III 部的边界篇正是从协作中涌现的问题（穷举场景）出发做元审视，第 IV 部则把"谁决策"上升到"谁划界"。

**前向引用预告**：08b 使用了第 III 部《09：穷举的宿命》《09d：细碎处理与区域重构》《09e：提示词拉扯的边界》的命题，08c 使用了第 III 部全部七篇的命题——首次遇到可先跳读第 III 部对应篇目，或先接受结论、读完全书后再回读。

**给读者的话**：这一部有四篇，但它们是全书从"工程"走向"哲学"的转折点——"LLM 只填空，不决策"这句话，在第 IV 部会变成"AI 在圈内做工，人在圈外负责"。同一个判断，工程的表述和哲学的表述。
