# 第 III 部 · 09b｜方法论体系构建的沉淀：配置推动的穷举一致性——统一推动点位与误差的哲学

## 一、推动点位的谱系：四种推动方式

### 1.1 一切系统都需要一个"推动点位"

先退一步。任何一个由 LLM 参与的生成系统，都要回答同一个问题：**规则从哪里来，又在哪里生效？** 我把这个位置叫作"推动点位"——它是规则进入系统的地方，是"系统该按什么行为运转"这个问题的答案落地的位置。

推动点位不是一个比喻。它决定四件具体的事：

```text
1. 规则写在哪里         （文件？代码？数据库？模型参数？）
2. 规则以什么形态存在   （字符串？函数？JSON？自然语言？）
3. 谁消费规则           （解释器？分支逻辑？LLM 的 prompt？）
4. 规则变更时动哪里     （改一行代码？改一个文件？改一句话？）
```

第四个问题最隐蔽，也最致命。**规则变更时动哪里——这个问题的答案，就是推动点位的真实形态。** 如果改一个行为要翻三个文件、改五处逻辑、还要担心漏掉第六处，那么推动点位就是分散的；如果改一个行为只需要改一个文件里的一行声明，那么推动点位就是统一的。

### 1.2 四种推动方式：硬编码、代码推动、配置推动、LLM 推动

我在这条路上依次试过四种，每一种都留下了实证：

**硬编码。** 最早的形态。规则以字符串字面量、魔法数字、散落的 if/elif 直接写在业务逻辑里（01 的门禁钩子就是典型）。它的推动点位**不在任何显式位置**——规则就是代码本身，改规则就是改代码，改代码就是改行为。推动点位与实现完全重合，没有中间层。

**代码推动。** 规则从字面量升级为代码结构：策略类、工厂函数、注册表、装饰器。推动点位从"散落的 if"收敛到"类与函数的定义处"。比硬编码好——规则至少有一个家了。但它仍然是代码：改规则要改代码、要重新部署、要过代码审查，**非技术人员无法触碰推动点位**。

**配置推动。** 规则外置为数据：JSON、YAML、模板声明、`_meta.json`。代码负责**解释**配置，配置负责**声明**行为。推动点位第一次从代码中分离出来——代码只说"怎么执行"，配置说"执行什么"。这是分层的开始：**配置是声明层，代码是执行层，推动点位住在声明层。**

**LLM 推动。** 规则以自然语言写进 prompt，由模型在运行时解释。推动点位变成了"提示词里的那句话"。这是最灵活的推动——但它把解释权交给了概率。**LLM 推动的推动点位是存在的，但它是一个概率点位：同一句话，十次运行有十一种理解。**

### 1.3 我为什么最终停在配置推动

不是情怀，是三个硬理由。

**第一，LLM 推动把"偏差"变成了"随机"。** 这是我的核心关切（09）。LLM 推动的偏差是概率性的——你无法预测它会偏到哪，无法枚举它会怎么偏，自然也无法校准。推动点位变成了一个混沌系统的人海口：你推的是规则，进来的是噪声。

**第二，硬编码和代码推动的偏差是"分散"的。** 点位藏在代码里，偏差也藏在代码里。规则改了一处、另一处没改——这种偏差不是"偏"，是"裂"。它甚至不给你一个可观察的误差形态，因为每一处点位的偏差互相独立、互不知情。分散的点位意味着分散的枚举空间：校准 N 个点位，等于做 N 次独立的校准。

**第三，配置推动的偏差是"一致"的——而一致是校准的前提。** 这是全文的核心，展开在第二章。

> **核心判断：四种推动方式，本质是四种"偏差分布"。硬编码的偏差藏在代码里，代码推动的偏差集中在类与函数里，LLM 推动的偏差散落在概率里，只有配置推动的偏差，坐在一个可以被指认、被枚举、被校准的位置上。**


## 二、统一推动点位的真正价值：有限枚举

### 2.1 不可穷举，但可以有限枚举

承接 09 的结论：只要目的是稳定，就没有跑出穷举。但穷举有一个量级的差别——**穷举什么**。

配置推动之前，我穷举的是"行为"：枚举 LLM 可能犯的每一种错（01），枚举该查的所有角度（06），枚举流程的所有节点（05）。行为空间是开放的——它跟着业务扩张，跟着模型版本漂移，跟着 prompt 措辞变化。穷举行为，是一场打不完的仗。

配置推动之后，穷举的对象变了：我不再穷举行为，而是穷举**点位**。点位是声明层里的条目：一个字段、一个开关、一个档位、一个映射。**点位空间是封闭的——它就是你配置文件里的那张表。** 表有多长，枚举空间就有多大；表是有限的，枚举就是有限的。

这就是"不可穷举但可有限枚举"的精确含义：

```text
行为空间：开放的、随业务漂移的、不可枚举的
点位空间：封闭的、随配置表固定的、可有限枚举的
```

同一个系统，两种穷举成本。前者是"穷举的宿命"（09），后者是"宿命内的自由"——你改变不了穷举本身，但你可以选择穷举的坐标系。**配置推动，就是把穷举从行为坐标系搬到点位坐标系。**

### 2.2 偏差一致：有限枚举的红利

点位有限，意味着偏差有限。更重要的不是数量，而是**一致性**。

举一个具体的例子。structured-writer 里 meta 字段有 `user/auto/llm` 三种来源模式（这是模板文档里早就写明的语义，此前它只是文档）。当字段从配置声明中读取时，每一个字段的偏差行为是**同一套规则产生**的：user 字段——用户填了就用、没填就空；auto 字段——用户填了抄入、没填 LLM 生成；llm 字段——一律 LLM 生成。一百个字段，只有三种偏差形态。

一致性带来的第一个红利是**可预测**：看到任意一个字段，我就知道它的偏差会怎么表现——不需要为每个字段单独做心理实验。

一致性带来的第二个红利是**可枚举**：三种形态，就是三行校准表。我可以把一百个字段的偏差，压缩成三行规则来审视。

一致性带来的第三个红利是**可回归**：配置变了，我知道全系统的偏差会**同步地**变——不会出现"改了 A 字段，B 字段行为没跟上"的裂痕。

### 2.3 对照：分散点位的枚举爆炸

反证更容易看清。如果推动点位分散在代码里——这里一个 if，那里一个特殊分支，prompt 里还藏着一句隐含规则——那么偏差就是**每处独立**的：

```text
点位 A 的偏差：……（只有 A 的开发者知道）
点位 B 的偏差：……（B 的逻辑与 A 无关）
点位 C 的偏差：……（C 藏在 prompt 里，随模型漂移）
```

校准这样的系统，等于对每个点位单独做一遍"发现-诊断-修复-回归"。而且点位之间会互相干扰：修好 A，B 的行为边界跟着变；改了 prompt，C 和 A 一起漂。**分散点位的枚举成本是乘积级的，统一点位的枚举成本是加法级的。** 这就是我选配置推动的算法级理由。

> **核心判断：统一推动点位 = 把"穷举行为"降维成"枚举差异"。穷举的对象从开放空间变成封闭表，偏差从每处独立变成一族一致。**


## 三、偏差一致的两种命运：误差抵消与误差补正

### 3.1 一致的偏差才有"命运"可言

偏差一致之后，系统面对一个岔路口：这些一致的偏差，最终会走向哪里？

这里要小心一个直觉陷阱。直觉上，"偏差一致"听起来是坏事——一致地偏，不是越偏越多吗？不是。**一致地偏，是偏在同一个方向、同一个量级上；这种偏差是可计算的。可计算的偏差，就有两种可设计的命运。**

### 3.2 命运一：误差抵消——错着错着就对了

误差抵消不是玄学，它有严格的成立条件：**当偏差是系统性且方向可设计时，可以通过构造相反的偏差让它相互抵消。**

举例。配置推动下，如果我知道所有字段在"auto 未填"时都会向"LLM 自由发挥"这个方向偏，那么我可以在**同一个点位**上做一个收敛动作——把"未填"的默认行为从"自由发挥"改为"显式留空 + 明确标注"。偏差还是偏差，但方向被设计成"可识别"：留空的字段一眼可见，不会再被误当成用户决策。

更普遍的形式是**配对**：一个点位负责"放开"（auto 允许 LLM 生成），另一个点位负责"收紧"（校验层对生成结果做形态约束）。放开引入的偏差，被收紧吸收——这不是消除偏差，是让两处偏差在同一坐标系里**相减**。

**"错着错着就对了"的真正含义：不是运气，而是设计——两个可预测的错，在同一个点位体系里，可以构造出互相抵消的相位。**

### 3.3 命运二：误差补正——统一有限枚举的误差更容易被统一校准

误差抵消要求偏差方向可设计；不是所有偏差都能设计方向。这时走第二条路：**误差补正——接受偏差存在，用一张校准表把它拉回来。**

补正的前提，恰恰是"有限枚举 + 一致"。因为：

```
偏差有限（枚举得到） → 校准表有界（一张表装得下）
偏差一致（同一规则产生） → 校准规则统一（一行规则校准一族偏差）
偏差可回归（改配置全系统同步变） → 校准可迭代（每次校准的结果可复用）
```

分散点位的偏差无法补正，因为它不满足第二条：每处偏差的来源不同，一张校准表套不上去。**补正是一种批量操作，只对一族一致的偏差有效。**

structured-writer 里有一个现成的例子：子结构字数。早期每个子结构的字数显示都取档位上限（短篇全 1500），因为显示层的 fallback 是"取 word_count_target.max"。这是一个**一致的偏差**——不是某个字段错了，是所有字段以同一规则偏向了上限。修复它只需要改一个点位：让 LLM 在规划时给出每段的目标字数，显示层优先用 LLM 的值。**一处改动，校准了所有章节、所有段落的字数偏差。** 如果当初每段的字数逻辑散落在不同代码里（有的取 max、有的取中值、有的写死），这次校准就得逐段进行——而那正是分散点位的宿命。

### 3.4 两种命运的公共前提：点位还在那里

值得强调的是，误差抵消与误差补正是两条不同的路，但它们的**公共前提只有一个：点位还在那里**。如果推动点位分散、或隐没在代码与 prompt 里，那么偏差既不可设计（无法抵消），也不可枚举（无法补正）——它只剩第三种命运：**不可见的漂移**。漂移是最坏的情况，因为它既不偏左也不偏右，而是"不知道在哪"。

> **核心判断：一致的偏差不是缺陷，是资产——它让误差有了两种可设计的命运（抵消或补正），而这两种命运都要求同一个前提：推动点位统一且可指认。分散点位的偏差只有一种命运：不可见的漂移。**


## 四、标准化的意义：误差受控优先于靶心偏差

### 4.1 三个概念：精密度、正确度、准确度

走到这里，需要把三个经常被混用的词分开。按计量学标准（JJF 1001-2011《通用计量术语及定义》，等同国际 VIM3）：

- **正确度（trueness）**：测量结果的**平均位置**与真值的接近程度——"靶心偏差几毫米"。它描述的是系统偏倚（bias）。**它是理论量：需要无穷多次测量的均值才能定义，有限情况下观测不到。**
- **精密度（precision）**：重复测量结果之间的接近程度——"每次落在同一个位置"。它描述的是随机离散（variance）。**它是可观测的：跑十次看离散就知道。**
- **准确度（accuracy）**：测量结果的综合表现——**粗略等于精密度 + 正确度**。工程量化即 `MSE = bias² + variance`（均方误差 = 系统偏倚² + 随机方差）。通俗地说，**准确度就是"多次测量下的平均'正确度'"**——你测到的每一次落点，既被正确度（平均位置）支配，又被精密度（离散）污染。

工程语言里它们还有另一对投影：**偏差（bias）与方差（variance）**。正确度对应偏差，精密度对应方差。经典的偏差-方差权衡说的是：你可以牺牲一点偏差，换取大幅的方差下降——因为方差是你可以校准的东西，而偏差的"真值"你往往看不到。

### 4.2 真值到底真不真：有限情况下的判断依据

为什么偏差-方差权衡在 LLM 系统里如此尖锐？因为**真值不可达**。

在 10a 里我已经论证过：伦理问题没有可穷尽的边界，做工需要二元论断，而边界不可穷尽——于是只能画圈，画圈就是垄断划界权。那个论证的底层逻辑，和这里完全一致：**只要真值不可直接观测，对"正确度"的追求就是对一个不可观测量的追求；你能观测到的只有"准确度"——而准确度里含着精密度：精密度差，你连"平均正确度"都估不准（均值标准误 σ/√n 大）。**

在有限的情况下（有限的枚举、有限的样本、有限的运行次数），我们真正能观测到的只有准确度——而准确度被精密度锁着。正确度是一个信仰，准确度是一个事实；精密度是通往准确度观测的唯一通道。**工程决策应该建立在事实上。**

### 4.3 误差受控比靶心偏差几毫米更值得关注

由此得出全文最实用的一条判断：

> **大多数时候，误差受控比靶心偏差几毫米更值得关注。**

展开说——这里"误差受控"说的是**精密度**，"靶心偏差几毫米"说的是**正确度**：

```
精密度差（每次乱跳）：均值漂移不可控 → 准确度观测不可靠 → 正确度评估不准 → 不可校准
精密度好（每次同一点）：均值稳定 → 准确度可观测 → 正确度可间接逼近 → 可收敛
```

精密度好的系统可能"偏"（平均落点离真值有固定距离——正确度差），但它是**可治理**的：你可以声明它的偏差，校准它的偏差，甚至设计它的偏差（第三章的抵消与补正）。精密度差的系统看起来"准"（某一次碰巧接近真值），但它是**不可治理**的——你无法对它做任何系统性改进，每次修修补补都是打地鼠。

标准化的意义正在于此。标准化不是"把偏差消灭到零"——那是正确度崇拜。**标准化是把精密度先钉住：统一的推动点位、统一的字段语义、统一的枚举表，让每次落点可预测**——然后正确度才谈得上校准（补正）或设计（抵消）。标准化的产物不是"准"，是"稳"——而稳是通往准的唯一可行路径，因为只有稳，校准才有落点。

### 4.4 校准的终点：声明偏差，而非消灭偏差

最后一步是心态转换。配置推动的系统，最终形态不是"没有偏差"，而是**"偏差被声明"**：

```
未标准化的系统：有偏差，但偏差不可见 → 出问题时只能猜
标准化的系统：有偏差，但偏差在配置表里 → 出问题时先看表
```

我写 08a 时强调的是"前置规范大于后置验证"——那是在流程维度上把问题提前。这里是在**偏差维度**上把问题提前：与其等偏差在运行中显现，不如在配置声明时就知道它会在哪里出现、以什么形态出现。**声明偏差，是比消灭偏差更高明的工程姿态——前者是管理现实，后者是否认现实。**

> **核心判断：精密度优先于正确度，误差受控优先于靶心偏差。因为正确度是不可观测的理论量（无穷多次均值才定义），可观测的只有准确度——而准确度 = 精密度 + 正确度，被精密度锁死。标准化 = 先把精密度钉住（统一点位、一致偏差），让正确度谈得上校准；把偏差从"不可见的漂移"转化为"可声明的资产"。**


## 五、回到实践：structured-writer 的两个实证

### 5.1 实证一：meta 三模式统一——从"字段特判"到"配置声明"

此前，structured-writer 的 meta 字段处理是**字段特判**式的：标题有"四级优先级"（用户填了用/没填 LLM 提炼/截断/兜底），叙事视角有"代码级固化"（单独一段 if 覆盖 LLM 返回）——每个字段一套逻辑，散落在 planner.py 与 novel_bridge.py 里。

这就是典型的**分散点位**。表面看每个字段都"处理"了，但偏差行为互不一致：标题的偏差是"四级优先级"产生的，叙事视角的偏差是"代码固化"产生的，下一个字段的偏差又会是另一套逻辑产生的。校准无从谈起——因为根本没有一张表可以描述"所有字段的偏差"。

修复只做了一件事：**把点位统一到配置声明**。模板的 meta 数组就是推动点位：

```json
{"name": "标题", "source": "auto", "desc": "小说标题"}
{"name": "题材", "source": "user", "desc": "题材"}
{"name": "叙事视角", "source": "auto", "desc": "视角"}
```

三个 source（user/auto/llm）一套语义，所有字段共用。一百个字段的偏差，压缩成三行规则；三行规则，就是那张校准表。**这次修复没有增加任何字段级 if——它只是把偏差从"每处独立"改成了"一族一致"。**

### 5.2 实证二：叙事视角——从"标签"到"可执行规则"

叙事视角是另一个点位案例。早期系统里，用户填了"第一人称"，LLM 写作时还是写第三人称。排查发现：规划层正常（state 里 narrative_voice = "第一人称"），但写作上下文里它只是一行**标签**——"叙事视角: 第一人称"——LLM 看到了，但不知道该怎么执行。

这不是点位缺失（点位在 state 里好好的），而是**点位与执行的偏差不可见**：标签与行为之间的翻译，交给了 LLM 的概率。修复是在同一个点位（writing_style 配置）上，把标签升级为可执行规则：

```text
第一人称：正文必须以「我」作为叙述者展开，禁止用「他/她/主角姓名」作为主角的叙述主语
```

并把这条规则声明为最高优先级（system prompt 层）。**校准的不是输出，是点位与行为之间的翻译层。** 这个翻译层，配置推动系统里是声明的一部分；在分散点位系统里，它藏在每个 prompt 的措辞里，不可枚举、不可校准。

### 5.3 两个实证的共同结构

两个实证看起来不同（一个管字段、一个管视角），结构完全一致：

```
发现问题 → 偏差不可见（分散点位 / 翻译层在概率里）
统一点位 → 偏差变成声明（meta 数组 / writing_style 配置）
校准一致 → 一处改动全系统生效（三模式统一 / 视角强指令）
```

这正是第二章到第四章的完整演绎。配置推动不是一个"更好的实现"，它是**一个更可治理的偏差结构**。


## 六、边界与不足

诚实地说，配置推动不是银弹，它有三个已知边界：

**第一，点位本身的偏差仍然存在。** 配置表也会写错——字段名拼错、语义声明与消费代码不一致、文档与配置漂移。配置推动把偏差从"执行层"搬到了"声明层"，但没有消灭偏差。它的优势是：声明层的偏差是**可见且可审计**的——你有东西可看、可查、可 diff。

**第二，配置推动要求"可声明的规则"。** 不是所有规则都能外置成数据。有些规则是程序性的（依赖运行时上下文、跨模块状态），硬塞进配置反而制造出"伪声明"——看起来是配置，实际上需要代码配合才能成立。判断标准很简单：**一个配置项，如果离开代码上下文就无法被理解，它就不是配置，是披着配置外衣的代码。** 遇到这种，诚实地留在代码里，比强行外置更符合配置推动的精神。

**第三，LLM 推动没有消失，它被降级了。** 配置推动的系统里，LLM 仍然存在——但它的角色从"规则的来源"降级为"规则的服务对象"：配置声明"叙事视角是第一人称"，LLM 负责在规则内完成表达。这呼应 04 与 05：LLM 从"大脑"降级为"胶水"、从"主体"降级为"执行器"。**配置推动不是消灭 LLM 推动，而是给 LLM 推动划定坐标系。**


## 结语

回到最初的问题：为什么选择配置推动，而不是硬编码、代码推动，甚至 LLM 推动？

因为配置推动是**统一的推动点位**。统一推动点位意味着：虽然不可穷举，但可以有限枚举；有限枚举意味着偏差一致；一致的偏差只有两种命运——误差抵消，或者误差补正。而这两种命运，都要求点位还在那里。

标准化的意义也在于此：大多数时候，误差受控（精密度）比靶心偏差几毫米（正确度）更值得关注。因为正确度是不可观测的理论量，有限情况下你终归只能看准确度——而准确度 = 精密度 + 正确度，被精密度锁着。

从 01 的硬约束，到 09 的穷举宿命，再到这一篇的配置推动——我做的其实一直是同一件事：**给 LLM 的随机误差找一个可治理的座位。** 配置推动不是最正确的答案，它是最可校准的答案。而在这个真值不可达的世界里，可校准，就是工程意义上的真理。

最后补一个可操作的落脚点：本篇反复出现的"精密度优先于正确度""偏差一致才谈得上校准"，都可以直接观测。**silprespec-emulator**（见附录 B 工具索引）对同一输入并行执行 N 次，输出跨 run 填入一致率——这就是"精密度"的直观读数：一致率稳定，说明偏差可枚举、可校准；一致率乱跳，说明点位还没统一。想在自家场景验证"配置推动是否到位"，在实验台上选对应方式跑一轮重现性实验，比争论更有说服力。
