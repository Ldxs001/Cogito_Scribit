# 成书排版（五）：元数据排版——字数、章数与版本号

> 一本书除了正文，还有一组"关于书的数字"：多少字、多少章、什么版本。这些数字出现在封面、版权页、落地页、下载链接上——读者对一本书的第一印象往往来自它们。本文展开元数据排版的规则与逻辑：字数六口径与一个对外口径、章数的构成、版本号的规则，以及三者"三端一致"的纪律。边界声明：本文覆盖元数据级；源稿、元素、骨架、页面各级由前四篇承担，规则体系与执行管线由后续篇目承担 [1][2]。
>

## 一、引子：一个数字错了，全链路露馅

书的对外数字有个特性：**同一个数字出现在多处，任何一处落后都会露馅。** 一次真实教训：书已经收到新章（35 章），在线阅读落地页却还写着旧字数、旧章数、旧版本号，落后了两个版本——读者点开落地页，看到 33 章，下载的书是 35 章 [3]。

元数据排版的全部工作，就是让这些数字在多处落点保持一致，并且口径可复现。它不是"填几个数字"的杂活，是排版——数字在书上的排布，和正文在页面上的排布一样有规则。

## 二、字数：六口径，一个对外口径

字数统计脚本给出六个口径 [1]：

| 口径 | 算法 | 用途 |
|---|---|---|
| ① 总字符 | 全文长度（含空白与 md 语法） | 原始规模参考 |
| ② 去空白 | 去除全部空白后长度 | 紧凑规模 |
| ③ 纯汉字 | 汉字（CJK 统一表意文字）计数 | 中文体量 |
| ④ 汉字+中文标点 | ③ + 全角标点区 | 接近阅读量 |
| ⑤ 去语法 | 去 md 符号后去空白 | 可见内容量 |
| **⑥ 出版折算** | **汉字数 + 英文单词数 + 连续数字串数** | **对外唯一口径** |

排版逻辑：**对内多个口径各有用途，对外只认一个。** ③ 纯汉字适合讲"中文体量"——做对比时（这版比上版多多少字）用③最干净，它不受标点与英文影响；⑤ 去语法适合估算"读者实际看到的可见内容"——排版审查时用，看一页密度是否过载；但它们都不是出版口径——中文出版折算惯例是"汉字 + 英文单词 + 数字串"混合计，⑥ 就是按这个口径实现 [1]。对外（版权页、落地页、README）只写⑥的数，杜绝"有人说 16 万字、有人说 14 万字"的口径打架。

口径的分工本身也是排版：**统计口径服务于统计目的**——审查用⑤、对比用③、发布用⑥，一个脚本输出六个口径，取哪个看场合，但对外只有一个。

一次真实实践：全书内容调整后，⑥ 出版折算从 161,808 变成 161,955——变化只有 147 字，来自一次读者条目的增补（为书新增了一类读者的导语）[4]。对外表述从"约 16.5 万字"改为"约 16.2 万字"，三处落点（书目录 README、根 README、落地页）同时回填 [4]。**口径定了，数字变了就是变了，三处一起变。** 这个案例还说明一个细节：口径的敏感度——147 字的增补在 16 万字的体量里约等于 0.09%，但对外表述必须跟着变，因为"约 16.2 万"是读者可核对的承诺，不是四舍五入的游戏。（注：161,808 → 161,955 为 2026-08-28 当日实测；2026-09-01 复测为 161,962——字数随内容持续变化，口径与回填规则不变 [4]。）

## 三、章数：35 章的口径构成

章数同样有口径：本书 35 章 = 正文 21 篇 + 四部导读 4 篇 + 结语 1 篇 + 前置页 3 篇（版权页/序言/阅读指南）+ 附录 6 篇 [2]。

排版逻辑：**章数口径必须可复现。** 读者在落地页看到"35 章"，应该能推算出 35 从哪来。如果口径含糊（正文算不算导读？附录算不算章？），章数就变成一个无法核对的数字。35 的口径写进规范，新增一篇正文 → 章数 +1，新增一个附录 → 章数 +1 并更新口径公式 [2]。章数不是拍脑袋的统计，是有构成公式的数字。

章数的历史本身就是版式的演化记录：32 章（四部 + 六篇扩容）→ 33 章（第 IV 部扩容）→ 34 章（附录 F 端到端实测）→ 35 章（09f 入书完结）[2]。每一次章数变化都对应一次骨架变更（见本系列第三篇的"七处同步"）——章数口径的构成公式与骨架变更同步演进，两者互相印证：骨架多了什么，公式里就多了什么。

## 四、版本号：规则与三端一致

**版权页的版本记录是版本号的历史形态。** 版权页上除了当前的版本号，还有一条逐次递增的版本记录：每次变更列一行——版本号、变更内容（新增哪些篇、动了哪些部）、章数变到多少 [4]。**版本号是当前的锚，版本记录是变更的档案**，两者都在版权页上：一个指向现在（读者看到"v1.2.0"就知道当前是什么），一个记录过去（想追溯这版改了什么，逐条可查）。版本号只写当前，版本记录只写历史，各司其职——这也是元数据排版"一个落点一个职责"的体现。

版本规则：新增篇目 / 四部结构变化 / 章节数变化 → 次版本 +1（如 v1.2.0 → v1.3.0）；纯错字 / 格式修正 → 修订号 +1。**章数变化与版本号变化必须同时发生**——章数变了版本不 bump，读者看到"35 章 v1.2.0"，无法判断这个版本是否包含新增内容 [2]。

这个规则的粒度值得展开：次版本号管"结构变化"（加了篇、动了部、变了章数），修订号管"内容修正"（错字、格式）。它排的是"变更的语义"——读者从版本号就能读出这版改了多大：次版本动了，是结构级；修订号动了，是内容级。版本号是变更的摘要，粒度定错了，摘要就失真。

三端一致校验：**版权页记录的版本号 == 根 README 的发行 tag == 落地页 PDF 链接里的版本号**，任一不一致即失败 [2]。这三个落点对应三种读者：翻开书看版权页的、在仓库看 README 的、从落地页下载的——三种人看到的版本号必须是同一个。三个落点的角色各不相同：版权页是书内的（纸面或电子书翻到最前页），README 是仓库的（开发者语境），落地页是发布的（读者入口）——**介质不同、数字必须相同**，这就是三端一致的排版逻辑：元数据不随介质漂移。

版本号还决定发行：书出打印版走 GitHub/Gitee 双平台 Release（tag `book-vX.Y.Z` + PDF 附件），附件随内容更新同步替换——版本号不变，附件内容可以更新；版本号变了，发布新 tag [2][4]。发行侧的替换也有排版纪律：GitHub 换附件是"删旧传新"，Gitee 同名上传会变成新增而不是覆盖——必须先按目标文件名上传、再查附件列表删掉旧条目，否则同一个文件出现两条记录，读者下载时无法区分哪个是新版。**元数据排版不止管书页上的数字，还管发布时数字与附件的一致性。** 版本号是书对外身份的锚点：它同时出现在封面、版权页、README、落地页链接、Release tag 与附件名里——一个锚点，六处悬挂，任何一处漂移，读者对"这版书"的认知就出现裂痕。

## 五、结语：数字是书的元排版

字数、章数、版本号，是"关于书的排版"——它们不排正文，排的是读者对书的认知。六口径一个对外口径，让"多少字"可复现；35 章有构成公式，让"多少章"可核对；版本号三端一致，让"哪个版本"无歧义。三个数字合起来，是书对外的第一张脸——这张脸不能糊，因为它是读者决定"要不要打开这本书"的依据。

到这里，成书排版五层收齐：源稿排版定写法（一），元素排版定一章（二），骨架排版定章序（三），页面排版定纸面（四），元数据排版定对外数字（五）。五层合起来是一本书从"作者写"到"读者读"的完整排版链路——每一层都有规则，每一条规则都有它的排版逻辑。

为什么元数据放在最后讲？因为它依赖前四层的结果：字数依赖成书后的内容，章数依赖骨架的构成，版本号依赖全部变更——**元数据是前四层排版的"结算单"**，前四层定了，它才有数可算。反过来，它又是读者最先接触的一层：落地页第一眼看到的就是字数、章数、版本号。排版链路的最后一环，恰恰是读者认知的第一环——这也是为什么"一个数字错了全链路露馅"值得单独写成一篇：前四层排得再好，结算单错了，读者对整本书的第一印象就错了。
